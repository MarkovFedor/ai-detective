## Участник 2: BM25, p-adic организация, контекст

### 1. Предобработка для BM25
- **Задача:** выбрать токенизацию для BM25 по 40 утверждениям.
- **Запрос:** «сравни варианты предобработки для rank-bm25 на русском».
- **Предложение ассистента:** сравнить без нормализации / стемминг Snowball / леммы pymorphy3 по доле эталонных evidence в top-15.
- **Решение:** леммы pymorphy3 + стоп-слова, корпус — поле `text` утверждений.
- **Проверка:** без нормализации 19/23 эталонных id в top-15, со стеммингом и леммами — 21/23; добавление `evidence` к тексту ничего не дало.

### 2. Отклонённое предложение: транслитерация кодов пропусков
- **Предложение ассистента:** транслитерировать латинские токены (`SEMENOV-P` → «семенов»), чтобы BM25 находил C16 по вопросу Q10.
- **Решение:** отклонено.
- **Проверка:** recall@15 не изменился (21/23), C16 всё равно не попадает в top-15; лишняя сложность и подгонка под эталон.

### 3. Ошибка p-adic кодирования: время по created_at
- **Задача:** уровень a2 (до/во время/после события).
- **Первый вариант:** брать `created_at` документа.
- **Ошибка:** все показания написаны 18–19 мая, поэтому все свидетельства попадали в «после», хотя описывают ночь 16 мая.
- **Решение:** a2 считается по времени факта из текста утверждения; для 7 утверждений без часов — ручная таблица `TIME_OVERRIDES` с обоснованием.
- **Проверка:** вывод `python -m src.padic` просмотрен вручную по всем 40 утверждениям; тест `test_known_paths`.

### 4. Расстояние: префикс vs abs
- **Предложение ассистента:** считать расстояние по общему префиксу пути и дополнительно через 3-адическую норму разности кодов |x−y|₃.
- **Решение:** основная функция — по префиксу; норма разности — как проверка эквивалентности. `abs(x−y)` не используется.
- **Проверка:** тест на всех 27×27 парах путей: обе формулы совпадают; тест, где abs дал бы противоположный порядок.

### 5. Генерация тестов

- **Решение:** ультраметрическое неравенство проверяется перебором всех 27³ троек путей; одинаковость B/C — для всех 12 вопросов.

### 8. Pydantic-схема: insufficient с answer != null
Задача: валидировать ответ LLM.
Первая версия схемы: проверяла только типы.
Ошибка: модель могла вернуть status="insufficient" и answer="Нет" — формально валидный JSON, но логически противоречивый.
Решение: model_validator, который проверяет: both → оба списка непустые; insufficient → answer=null; entailed → evidence_ids непустой и counterevidence_ids пустой.
Проверка: тесты на каждое правило (parse_model_answer с заведомо плохим dict → ValidationError).

### 10. Склейка JSON-строк при повторном stress_retry
Задача: дозаписать пропущенную Q05/C после ошибки токенов.
Первый запуск stress_retry: успешно дописал Q05/C.
Второй запуск: упал с JSONDecodeError: Extra data.
Причина: файл не заканчивался на \n, append дописал вторую запись в ту же строку — {...}{...}.
Решение: скрипт восстановления (разбить по '}{', убрать дубли по (question_id, mode), перезаписать); добавить ensure_trailing_newline перед append и терпимый load_existing с [warn].
Проверка: после восстановления 12 записей, дублей нет, пропусков нет, ошибок нет; повторный stress_retry не падает.
